# SB 강화학습 보행 및 Jetson–STM32 SPI 변경 계획

작성일: 2026-09-06

이 문서는 최초에 코드 변경 없이 작성한 설계 계획이다. 후속 요청에 따라 **Jetson 통신 패킷을 제외한 STM32 제어 코드를 구현했다.** 아래 1~12절은 설계 기준과 v3 제안을 보존하며, 실제 반영 범위와 내부 API는 13절에 정리한다. **SPI는 현재도 v2 고정 32바이트이며 아래 v3 패킷은 미구현 제안이다.**

## 1. 요청한 동작과 역할

- SB의 비어 있는 첫 위치를 강화학습 보행 모드로 사용한다. 현재 코드상 값은 `sb == 0`이다.
- 조종기는 전진 방향 선속도 `vx_cmd`와 회전 각속도 `wz_cmd`만 명령한다.
- Jetson은 강화학습 정책으로 몸체 Roll·Pitch 목표와 여섯 다리의 `(dx, dy, dz, dh)`를 계산해 STM32로 보낸다.
- STM32는 기존 보행기로 기본 착지 목표 `(x, y, z)`와 Swing 높이 `h`를 계산하고, Jetson의 잔차를 반영한 궤적·자세 제어·IK·서보 출력을 수행한다.

정책 출력은 `2 + 6 × 4 = 26`개다. Roll·Pitch는 **몸체 절대 자세 목표**로, 다리 출력만 **기본값에 더하는 잔차**로 해석한다. 이는 이번 계획의 명시적 설계 기준이다. 정책이 자세 잔차를 출력하도록 학습되었다면 Jetson에서 기준 자세와 합산해 이 인터페이스의 절대 목표로 변환한다.

```text
조종기 → STM32: SB 모드 선택, vx_cmd, wz_cmd
STM32 → Jetson: 센서 + 처리된 조종 명령 + 기본 착지/높이 + 보행 상태
Jetson → STM32: roll_ref, pitch_ref, Leg 1~6의 dx/dy/dz/dh
STM32: 기본 계획 + 잔차 → 경로 검증 → 발 궤적 → 자세 보정 → IK → PWM
```

## 3. SB 및 조종 입력 변경

### 3.1 모드 선택 제안

| 입력 | 변경 후 동작 |
|---|---|
| SB 첫 위치 `0` | 서기가 완료된 상태에서 RL 모드를 요청한다. |
| SB 가운데 `1` | 기존 서기 요청을 유지한다. 서기 완료 후에는 기존 SC 모드 선택을 사용한다. |
| SB 끝 위치 `2` | RL을 종료하고 기존 착지 절차를 요청한다. |
| SE READY | RL보다 우선하여 이동을 정지하고 READY로 전환한다. |
| SD Kill / Safety Fault | 기존 최상위 차단 동작을 유지한다. |
| SC | SB 0에서는 RL이 SC보다 우선한다. SB 1에서는 기존 MANUAL·ARM·CORRECTION 선택을 유지한다. |
| S1 | 초기 RL 정책은 Tripod 회전 보행으로 고정하고 S1로 패턴을 바꾸지 않는다. |

SC와 S1 처리 방식은 초기 구현 제안이다. 보행 패턴을 정책 학습 조건과 일치시키기 위한 결정이며, Wave까지 학습한 정책으로 확장할 때 별도로 변경한다. ARM 동작은 기존 UART5의 실제 ARM 모드 허가에 따르므로 RL 진입 중 매니퓰레이터 동작을 허가하지 않는다. 물리적으로 위에 있는 SB 위치가 논리값 0으로 들어오는지는 실제 조종기의 CH6 보정값으로 확인한다.

RL 진입은 기존 서기 완료·초기 영점 정렬 완료·CRSF 연결·입력 `motion_armed`·READY의 0.2초 중립 확인·보행 허용 시험 단계·정상 센서를 충족한 뒤 허가한다. 부팅 또는 완전 착지 상태에서 SB 0만으로 자동 기립하지 않는다. 첫 정상 정책 명령을 받기 전에는 서 있는 상태로 기다린다.

SB 0에서 다른 모드로 나갈 때는 새 RL 명령을 차단하고 현재 발 위치를 보존하는 정지/착지 전이를 거친다. 보행 중 SC/SE/SB 변경 때문에 발 목표를 즉시 기본 위치로 되돌리지 않는다. 통신 오류로 정지한 뒤에는 SB를 RL 밖으로 옮겼다가 다시 진입하고 중립 확인을 거쳐 재시작하도록 한다.

### 3.2 두 개의 연속 명령

| 입력 | RL 모드의 의미 |
|---|---|
| Throttle | 기존 전처리·필터를 거친 X축 속도 `vx_cmd` |
| Yaw 짐벌 | 기존 회전 보행의 부호를 유지한 `wz_cmd` |
| Roll·Pitch 짐벌 | RL 자세 목표에 사용하지 않는다. 진입 중립 확인은 기존 규칙을 유지한다. |
| 횡이동·수직 이동 | 사용자 명령 `vy_cmd = 0`, `vz_cmd = 0`으로 둔다. |

현재 회전 보행은 `vx = ROBOT_MAX_LINEAR_SPEED_MPS × throttle_filter`, `wz = -ROBOT_MAX_YAW_RATE_RADPS × yaw_filter`를 사용한다. Jetson에는 raw 스틱값 대신 데드밴드·필터·속도 제한을 거친 SI 단위 명령을 전송한다. STM32 기본 보행기와 Jetson이 같은 명령을 사용해야 한다.

이 계획의 `vx_cmd`는 기존과 같은 부호 있는 전후 속도다. 따라서 후진도 기존 입력처럼 허용한다. 전진만 허용하려면 RL 모드에서 음수 속도를 0으로 제한하는 별도 요구로 확정한다. 기존 위치 피드백은 유지하고 Heading 자동 보정은 현재 설정인 비활성 상태를 유지하는 안으로 한다. 피드백이 추가한 보정은 사용자 자유도와 구분하며, 정책 학습에서도 같은 하위 제어 동작을 사용한다. Jetson에는 적용 중인 전체 twist `(vx, vy, vz, wz)`도 별도로 전달한다.

## 4. 잔차의 의미와 적용 위치

### 4.1 좌표·단위·다리 순서

- 길이는 m, 자세는 rad, 선속도는 m/s, 회전 속도는 rad/s를 사용한다.
- `(x, y, z)`는 기존 `FootTrajectory`가 사용하는 **몸체 자세 역회전 적용 전의 Body 발 좌표**다. 관절 로컬 좌표나 World 좌표로 보내지 않는다.
- `h`는 Swing 중 직선 보간 경로에 더하는 들어 올림 높이다. 착지 높이 `z`와 구분한다. 현재 방사 방향 오프셋 `ROBOT_SWING_RADIAL_OFFSET_M`은 이 네 번째 파라미터에 포함하지 않는다.
- 다리 배열은 STM32 `leg = 0..5`, 문서상 Leg 1..6 순서다. 실제 배치는 **오른앞, 오른중간, 오른뒤, 왼앞, 왼중간, 왼뒤**다. 다리마다 `dx, dy, dz, dh` 순서로 연속 배치한다. URDF의 관절 나열 순서를 그대로 가정하지 않는다.
- 기존 [좌표축 정의](../Controller/좌표축/README.md)에 따라 **+X 전진, +Y 왼쪽, +Z 위쪽, 오른손 회전**을 사용한다. Jetson 학습 좌표의 대응은 한 축씩 확인해 매핑표로 고정한다.

기존 관절각 송신은 Leg 1~3의 Joint 2, Leg 4~6의 Joint 3 부호를 반전한다. 이 관절각 전용 변환을 발 잔차에 그대로 적용하면 안 된다. IMU는 STM32 영점 보정을 적용한 자세를 기준으로 학습 좌표와 맞춘다.

### 4.2 다리별 목표 생성

다리 `i`에 대해 다음과 같이 정의한다.

```text
p_nominal[i] = (x_nominal[i], y_nominal[i], z_nominal[i])
p_target[i]  = p_nominal[i] + (dx[i], dy[i], dz[i])
h_target[i]  = clamp(h_nominal[i] + dh[i], h_min, h_max)

foot_path[i] = 기존 Swing 생성기(start[i], p_target[i], h_target[i], ...)
body_target = (roll_ref, pitch_ref) → 기존 자세 피드백 및 역회전 경로
```

`p_nominal`은 현재 발 위치가 아니라 **다음 Swing의 기본 착지 끝점**이다. 기존 `FootTrajectory_AdaptiveLeg()`의 `front` 계산을 기준으로 보행 속도·위상·착지 Z·접촉 적응을 반영한 기본 계획을 STM32가 만든다. `h_nominal`은 현재의 `clamp(ROBOT_SWING_HEIGHT_M + body_offset_m.z, MIN, MAX)`를 따른다. 현재 기본 높이는 0.20 m, 최소/최대는 0.05/0.25 m다. 기준값과 잔차 반영값을 별도 보관해 매 주기 잔차가 누적되지 않도록 한다.

현재의 `landing_target_z[]`, `swing_start[]`, `phase_twist`, 기본 높이를 다리별 착지 끝점·높이 계획으로 묶는 작업이 필요하다. 최종 `feet.foot[]`에 잔차를 매 주기 단순 가산하는 방식은 사용하지 않는다. 그 방식으로는 착지 끝점과 경로 높이의 의미를 보존할 수 없다.

### 4.3 수신과 실제 반영 시점

1. Jetson의 26개 값을 완전히 검증한 후 하나의 수신 스냅샷으로 교체한다. 서로 다른 패킷의 자세와 잔차를 조합하지 않는다.
2. Roll·Pitch 목표는 5 ms 제어 경계에서 최신 유효 명령을 소비하고 기존 자세 변화율 제한·작업공간 검사를 거쳐 추종한다.
3. 다리 잔차는 다음 위상의 경로 검사를 시작할 때 한 번 고정한다. 검증기와 실제 궤적 생성기는 동일한 기본 목표·잔차·높이를 사용한다.
4. 이미 시작한 Swing의 끝점과 높이는 이후 수신 패킷으로 덮어쓰지 않는다. 다음 계획 슬롯에서 새 잔차를 선택한다. Swing 도중 재계획은 별도 확장 사항이다.
5. 패킷에는 여섯 다리 값을 모두 보내지만 해당 계획의 Swing 마스크에 포함된 다리만 적용한다. 나머지 다리 값은 다음 위상에 재사용하지 않는다.
6. 접촉이 확정된 지지발은 기존 Touchdown latch를 우선한다. Early/Late landing·지지발 복구·공통 Z 복구에서도 잔차를 재가산하지 않는다. `landing_target_z[i]`에는 `dz`를 반영한 최종 착지 Z를 저장해 의도적인 높이 변경이 공통 Z 복구의 지형 오차로 오인되지 않게 한다.

즉, **26개 값의 수신은 원자적으로 처리하지만, 자세와 발 계획의 실제 반영 시점은 구분한다.** 정책 학습에서도 자세의 연속 갱신과 다리의 위상별 고정을 동일하게 모사한다.

기존 `WorkspaceLimiter_Gait()`의 경로 예측, `FootTrajectory_Step()`, `SwingTrajectory_Calculate()`에 같은 계획을 전달해야 한다. 이후 몸체 자세 변화에도 매 제어 주기 자세 제한·최종 발 제한·IK 검사를 유지한다. 현재 경로 샘플 검사만으로 임의의 잔차 경로 전체가 검증됐다고 가정하지 않고, 변경된 경로의 중간점과 지지 조건까지 검증 범위를 보완한다.

## 5. SPI 길이와 전송 방식 변경안

26개 출력을 `int16_t`로만 보내도 `26 × 2 = 52`바이트가 필요하다. 현재 24바이트 Payload에는 들어가지 않는다. `float32`로 보내면 출력만 104바이트다.

**권장 초안은 양방향 모두 고정 128바이트인 v3다.** 최소 동작 출력만 담는 64바이트안도 가능하지만, 이 계획은 관측 참조·세션·위상 식별자와 STM32의 기본 착지/높이 48바이트까지 한 프레임에 담는다. 조각 재조립과 다리별 시각 불일치를 피하고 필드 검증을 단순하게 하기 위한 선택이다.

| 항목 | v2 현재 | v3 제안 |
|---|---|---|
| 전송 길이 | 32바이트 | 양방향 128바이트 |
| 버전 | `2` | `3` |
| 공통 헤더 | 6바이트 | 6바이트 유지 |
| Payload | 24바이트 | 120바이트 |
| CRC 위치 / 범위 | 30~31 / 0~29 | 126~127 / 0~125 |
| STM32→Jetson | SENSOR `0x21` | RL_STATE `0x31` |
| Jetson→STM32 | COMMAND `0x22` | RL_COMMAND `0x32`, NOP `0x30` |
| 물리 연결 | SPI2 Slave, Jetson Master, Mode 0, DRDY | 유지 |

정수는 Little Endian, SPI 비트 순서는 MSB First로 유지한다. CRC는 기존 CRC-16/CCITT-FALSE(`poly=0x1021`, `init=0xFFFF`, 반사 없음, `xorout=0`)를 유지하며 검사 범위만 바꾼다. 구조체 메모리를 직접 전송하지 않고 바이트 오프셋에 명시적으로 패킹한다.

1 MHz에서 128바이트 교환의 순수 클록 시간은 `128 × 8 / 1,000,000 = 1.024 ms`다. 5 ms마다 교환하면 클록 점유율은 20.48%이며, 전이중이므로 송수신 시간을 두 배로 계산하지 않는다. 실제 제어 여유는 DMA 준비·파싱·추론·스케줄링을 포함해 측정한다.

STM32와 Jetson은 함께 v3로 전환한다. 고정 길이가 다르므로 버전 바이트만 바꾸거나 한쪽만 먼저 적용해서는 통신할 수 없다. v3에서는 32바이트 자동 호환을 두지 않는다.

## 6. v3 공통 헤더와 인코딩

| 바이트 | 크기 | 필드 | 정의 |
|---:|---:|---|---|
| 0 | 1 | MAGIC | `0xA5` |
| 1 | 1 | VERSION_TYPE | 상위 4비트 버전 3, 하위 4비트 종류 |
| 2~3 | 2 | SEQUENCE | STATE는 새 상태 생성 순번, COMMAND는 새 추론 결과 순번 |
| 4 | 1 | DELTA_TIME | 해당 송신 데이터 생성 간격, 100 us/LSB, 표현 범위 밖은 포화 |
| 5 | 1 | FLAGS | 방향별 정의를 사용한다. |
| 6~125 | 120 | PAYLOAD | 방향별 필드를 사용한다. |
| 126~127 | 2 | CRC16 | Byte 0~125의 CRC, Low byte 먼저 |

| 값 | 형식 | 1 LSB | 비고 |
|---|---|---|---|
| Roll·Pitch 목표, IMU 자세 | `int16_t` | 0.0001 rad | 기존 IMU 인코딩과 동일 |
| 기본 x/y/z/h, dx/dy/dz/dh | `int16_t` | 0.0001 m = 0.1 mm | 표현 범위 약 -3.2768~3.2767 m |
| vx | `int16_t` | 0.0001 m/s | 부호를 보존한다. |
| wz | `int16_t` | 0.0001 rad/s | 부호를 보존한다. |
| 보행 진행률 | `uint8_t` | 1/255 | 0~1을 0~255로 변환한다. |

송신은 반올림 후 인코딩하고 수신은 스케일로 나누어 복원한다. 표현 범위와 실제 허용 범위는 별개다. Jetson의 NaN·Inf·범위 밖 출력은 정수 변환 전에 거부하고, STM32에서도 RL 한계와 작업공간을 검사한다. 한계를 적용했다면 상태로 알려 학습/로그에서 원래 출력과 반영값을 혼동하지 않게 한다.

관절각 18개의 8비트 인코딩은 우선 유지한다. 약 1.059도/LSB이므로 정책 학습에도 같은 양자화를 반영한다. 관절 속도·IMU 각속도·가속도 등 추가 관측이 필요한 정책이면 실제 observation 정의를 먼저 확정하고 이 상태 패킷을 다시 설계한다. 현재 관측만으로 임의의 학습 모델을 실행할 수 있다고 가정하지 않는다.

## 7. Jetson → STM32: RL_COMMAND 배치

| 바이트 | 크기 | 필드 | 의미 |
|---:|---:|---|---|
| 0~5 | 6 | 공통 헤더 | VERSION_TYPE=`0x32` |
| 6~7 | 2 | OBS_SEQUENCE | 추론에 사용한 RL_STATE 순번 |
| 8~11 | 4 | SESSION_ID | 해당 RL 운용 세션 식별자 |
| 12~13 | 2 | PLAN_ID | 다리 잔차가 참조하는 기본 계획 번호 |
| 14 | 1 | PLAN_SWING_MASK | 해당 계획에서 Swing할 다리, bit 0~5 |
| 15 | 1 | RESERVED | 0 |
| 16~17 | 2 | ROLL_REF | 몸체 Roll 목표 |
| 18~19 | 2 | PITCH_REF | 몸체 Pitch 목표 |
| 20~27 | 8 | LEG1_RESIDUAL | dx1, dy1, dz1, dh1, 각각 int16 |
| 28~35 | 8 | LEG2_RESIDUAL | dx2, dy2, dz2, dh2 |
| 36~43 | 8 | LEG3_RESIDUAL | dx3, dy3, dz3, dh3 |
| 44~51 | 8 | LEG4_RESIDUAL | dx4, dy4, dz4, dh4 |
| 52~59 | 8 | LEG5_RESIDUAL | dx5, dy5, dz5, dh5 |
| 60~67 | 8 | LEG6_RESIDUAL | dx6, dy6, dz6, dh6 |
| 68~125 | 58 | RESERVED | 0 |
| 126~127 | 2 | CRC16 | 공통 정의 |

Byte 5 COMMAND FLAGS:

- bit 0 `ACTION_VALID`: 이번 추론 결과가 유효하다.
- bit 1 `POLICY_READY`: 모델·입출력 매핑 준비가 완료됐다.
- bit 2 `LEG_PLAN_VALID`: 다리 계획용 잔차를 포함한다.
- bit 3~7: 예약, 0.

bit 0·1이 모두 1이어야 정상 정책 명령으로 소비한다. `LEG_PLAN_VALID=0`이면 자세 전용 명령이며 PLAN_ID·마스크·잔차는 모두 0으로 보낸다. 정지 중 다음 발 계획이 없어도 자세 명령과 정책 생존 여부를 계속 갱신할 수 있다.

`LEG_PLAN_VALID=1`이면 세션·관측·계획 ID·Swing 마스크 일치를 모두 확인한다. 검증이 닫힌 계획에서는 같은 계획에 대한 정상 새 명령의 자세만 소비할 수 있고, 잔차는 이미 고정한 계획을 변경하지 않는다. 참조 불일치 패킷은 부분 적용하지 않고 통째로 거부한다.

NOP는 VERSION_TYPE=`0x30`, 나머지 헤더 필드와 Payload는 0으로 채우고 CRC를 계산한다. NOP는 읽기 전용 교환에 사용하며 명령 유효시간을 연장하지 않는다. v2의 전체 0 Dummy 허용을 유지할 경우에도 진단용으로만 취급하고 RL 명령으로 인정하지 않는다.

## 8. STM32 → Jetson: RL_STATE 배치

| 바이트 | 크기 | 필드 | 의미 |
|---:|---:|---|---|
| 0~5 | 6 | 공통 헤더 | VERSION_TYPE=`0x31`, FLAGS bit 0~5는 발 접촉 |
| 6~23 | 18 | JOINT[18] | 기존 v2의 순서·부호·인코딩 유지 |
| 24~29 | 6 | IMU_ROLL/PITCH/YAW | 기존 v2 자세 필드 유지 |
| 30~31 | 2 | VX_CMD | STM32와 정책이 공유하는 처리된 사용자 속도 |
| 32~33 | 2 | WZ_CMD | STM32와 정책이 공유하는 처리된 사용자 회전 속도 |
| 34 | 1 | ACTIVE_MODE | 실제 RobotControlMode, 기존 번호 유지 후 RL 추가 |
| 35 | 1 | RL_STATE | 0=비활성, 1=대기, 2=활성, 3=정지 진행, 4=오류로 재진입 필요 |
| 36~39 | 4 | SESSION_ID | 현재 RL 세션 |
| 40~41 | 2 | PLAN_ID | 현재 공개된 기본 계획 번호 |
| 42 | 1 | PLAN_SWING_MASK | 해당 계획에서 Swing할 다리 |
| 43 | 1 | STATE_FLAGS | 아래 정의 |
| 44~45 | 2 | POSE_REF_SEQUENCE | 자세 목표로 마지막 소비한 COMMAND 순번 |
| 46~47 | 2 | LEG_ACTION_SEQUENCE | 실제 보행 위상 시작에 사용한 COMMAND 순번 |
| 48~53 | 6 | LEG_STATE[6] | STANCE·SWING·LATE_LANDING 등 기존 다리 상태 번호 |
| 54~59 | 6 | LEG_PROGRESS[6] | 다리별 진행률 |
| 60~107 | 48 | NOMINAL[6][4] | Leg 1~6의 기본 x, y, z, h, 각각 int16 |
| 108~111 | 4 | SNAPSHOT_TIME_MS | 상태를 캡처한 STM32 로컬 시각, uint32 |
| 112~113 | 2 | VX_APPLIED | 현재 위상에 적용 중인 제한 후 twist.vx |
| 114~115 | 2 | VY_APPLIED | 위치 피드백 등을 포함한 적용 twist.vy, vx와 같은 스케일 |
| 116~117 | 2 | VZ_APPLIED | 적용 twist.vz, vx와 같은 스케일 |
| 118~119 | 2 | WZ_APPLIED | 현재 적용 중인 제한 후 twist.wz |
| 120 | 1 | ACK_STATUS | bit 0=자세 순번 유효, bit 1=다리 순번 유효, bit 2~4=거부 이유, bit 5~7=예약 0 |
| 121 | 1 | PLAN_STATUS | 0=계획 없음, 1=잔차 대기, 2=검증 중, 3=적용 중, 4=거부 |
| 122~123 | 2 | LEG_APPLIED_PLAN_ID | 마지막 실제 보행에 사용한 계획 번호 |
| 124 | 1 | LIMIT_FLAGS | bit 0~5=다리별 제한 개입, bit 6=Roll, bit 7=Pitch |
| 125 | 1 | LEG_APPLIED_MASK | 마지막 실제 위상에 잔차를 적용한 다리 마스크 |
| 126~127 | 2 | CRC16 | 공통 정의 |

Byte 43 STATE_FLAGS는 bit 0=CRSF 연결, bit 1=입력 motion_armed, bit 2=Priority motion_armed, bit 3=서기 완료, bit 4=IMU 유효, bit 5=센서 최신성 충족, bit 6=Safety Fault, bit 7=실제 릴레이 하나 이상 ON으로 정의한다. 릴레이가 모두 OFF이면 기존처럼 관절을 0도로 인코딩하되, 이 비트로 전원 OFF 값을 실제 자세와 구분한다. 접촉 마스크의 bit 6~7, 다리 마스크의 bit 6~7도 0으로 둔다.

ACK_STATUS의 거부 이유는 0=없음, 1=형식/CRC, 2=순번, 3=세션, 4=관측 만료, 5=계획, 6=범위/경로, 7=모드/시간 초과다. 최근 거부 이유를 유지하고 정상 새 명령을 소비하면 0으로 갱신한다. 마지막 정상 명령의 수신 시각과 Timeout 계산은 STM32 내부 상태에 보관한다.

PLAN_STATUS가 0이면 PLAN_ID·마스크·NOMINAL을 0으로 보내고 Jetson은 이 값을 기본 발 위치로 해석하지 않는다. 나머지 상태에서는 동일 PLAN_ID의 기본 계획이 변하지 않아야 한다. 센서·명령·위상·기본 계획은 하나의 일관된 제어 스냅샷으로 송신한다.

POSE_REF_SEQUENCE는 목표를 소비했다는 뜻이며 몸체가 목표각에 도달했다는 뜻은 아니다. LEG_ACTION_SEQUENCE는 수신·후보 저장 시점이 아니라 검증된 계획으로 실제 위상을 시작할 때 갱신한다. 실제 자세는 IMU로 확인하고, 적용 다리·계획은 LEG_APPLIED_MASK와 LEG_APPLIED_PLAN_ID로 확인한다. 제한 비트는 현재 자세 처리 및 마지막 적용 다리 계획에 대한 결과로 유지하고 세션 초기화 시 지운다.

## 9. 계획 동기화와 실행 순서

1. STM32가 보행 요청으로 다음 기본 계획을 만들고 PLAN_ID·Swing 마스크·NOMINAL을 공개한다. **계획 생성은 RL 잔차 수신 전에도 가능해야 한다.** 발을 들어 올리는 위상 시작만 잔차/검증 완료를 기다린다.
2. Jetson이 해당 RL_STATE를 받아 추론하고 OBS_SEQUENCE·SESSION_ID·PLAN_ID·마스크를 되돌려 보낸다.
3. STM32는 새 명령을 검증하고 다음 5 ms 제어 경계에서 소비한다. 자세 목표는 제한을 거쳐 갱신한다.
4. 계획이 잔차 대기 상태이면 최신 후보 하나를 선택해 기본 계획과 함께 고정하고 경로 검사를 시작한다. 검사 중 새 패킷이 들어와도 검사를 매번 다시 시작하지 않는다.
5. 검증을 통과하면 그 계획으로 위상을 시작하고 다리 ACK를 갱신한다. 거부하면 PLAN_STATUS=4와 이유를 보내며 새 순번의 후보로 재시도한다. 검증 중 또는 실제 시작 전에 후보의 관측/명령 유효시간이 끝나면 후보와 검사를 취소하고 PLAN_STATUS=4, 거부 이유 4로 전환한다. 기본 계획이 그대로이면 같은 PLAN_ID에 대한 새 순번의 후보를 받으며, 그동안 발 위치를 유지한다.
6. 위상 적용 중 같은 PLAN_ID를 참조하는 새 패킷은 자세 갱신에 사용할 수 있다. 이미 시작한 다리 궤적에는 새 잔차를 반영하지 않는다.
7. 기본 목표·높이·보행 패턴·Swing 마스크·기준 속도가 달라지면 PLAN_ID를 증가시키고 새 계획을 공개한다. 이때 이전 대기 후보와 진행 중 검사를 취소한다. 이전 잔차를 새 기본 목표에 암묵적으로 이식하지 않는다.

작업공간 제한이 기본 속도나 착지 목표를 바꾸는 경우에도 새 기본 계획으로 다시 공개하거나 후보를 거부한다. 명령 대기 중 새 조종값은 다음 계획용으로 보관한다. 정지 요청과 Safety는 계획 고정보다 우선한다. 첫 진입·대기·검증·정지 단계에서도 상태 송신과 자세 전용 명령 처리는 계속 실행한다.

SPI는 한 트랜잭션에서 송수신이 동시에 진행된다. Jetson이 이번에 받는 상태로 계산한 결과는 다음 이후 트랜잭션에 보내야 한다. 해당 결과의 ACK도 STM32 제어가 소비한 뒤 생성한 상태에 나타난다. 고정 한 주기 지연을 가정하지 말고 관측 순번·계획 ID·반영 순번으로 추적한다.

## 10. 최신성·통신 중단 처리

다음 시간 값은 초기 검증용 제안이며 추론 지연 측정 후 학습과 펌웨어에 같은 값으로 확정한다.

| 항목 | 초기 제안 |
|---|---|
| STM32 제어 / SPI 교환 | 5 ms / 목표 200 Hz |
| Jetson 추론 | 20 ms / 목표 50 Hz |
| 관측 최대 나이 | STM32 캡처 기준 60 ms |
| 정상 새 정책 명령 Timeout | 100 ms |
| 다리 후보 적용 조건 | 위상 시작 시에도 후보가 유효시간 이내이고 같은 계획이어야 함 |
| DMA 거래/오래된 준비 프레임 재동기화 기준 | 초기 20 ms, 실제 Master 동작과 함께 검증 |

- 동일 추론 결과를 SPI 주기마다 다시 보내면 같은 COMMAND 순번을 사용한다. 중복은 새 명령이나 생존 신호로 세지 않는다. NOP도 Timeout을 갱신하지 않는다.
- 순번 차이 `d = (new - old) mod 65536`에서 `d == 0`은 중복, `0 < d < 32768`만 새 명령, 그 외는 과거/모호한 순번으로 거부한다. 유실 누적은 정상 전진 순번에만 적용한다. NOP는 COMMAND 순번 추적과 분리한다.
- STM32는 최근 송신 관측의 순번·캡처 시각·세션·계획을 짧은 이력으로 보관한다. OBS_SEQUENCE가 실제 송신한 관측인지 확인하고 로컬 시계로 나이를 검사한다. COMMAND의 DELTA_TIME이나 수신 시각만으로 관측의 최신성을 판단하지 않는다.
- 새 세션에서는 순번·관측 이력·대기 명령·ACK를 초기화한다. SESSION_ID는 RL 재진입 및 STM32 재부팅 전후에 재사용되지 않도록 발급해야 한다. 영속 부트 카운터와 진입 카운터 또는 재부팅을 구분하는 세션 교환 방식을 구현 때 정한다. 단순 RAM 카운터 0 초기화만으로 대체하지 않는다.
- 시간 초과, 모드 종료, 재부팅 시 기존 명령을 폐기한다. Jetson 재시작 후 순번이 초기화된 경우에는 새 RL 세션에서 다시 시작한다.
- 기존 SPI의 `transfer_active`에는 무기한 대기를 끝내는 처리가 없다. NSS 상태를 확인해 DMA 중단·오류 정리·DRDY Low·새 프레임 준비·재Arm 순서로 복구하는 경로를 추가한다. 전송 중 DMA 버퍼를 덮어쓰지 않는다.
- 미리 준비한 상태가 오래된 채 전송될 수 있으므로 SNAPSHOT_TIME_MS와 관측 이력으로 거부한다. Jetson이 멈췄다가 돌아온 첫 프레임으로 곧바로 보행을 허가하지 않는다.

RL 명령이 끊기면 새 Swing을 차단하고 사용자 이동 목표를 0으로 만든다. 이미 적용된 발 목표를 즉시 지우지 않고 기존 접촉/복구 로직으로 발을 정리해 READY 정지로 전환한다. 몸체 목표도 허용 변화율로 기본 자세에 복귀시킨다. 이때 RL 오류를 유지하고 재진입을 요구한다. CRSF 단절·착지 요청·Kill·Fault는 기존 안전 우선순위를 따르며, Jetson 통신 복구만으로 이를 해제하지 않는다.

특히 `hexapod_app.c`의 다음 두 항목은 함께 수정해야 한다.

2. 서보 릴레이 요청은 모드 whitelist를 사용한다. RL을 정상 운용 모드에 추가하되 초기 정렬·Kill·Fault·실제 보행 허가 조건을 함께 확인한다. enum만 추가하면 정상 보행 경로가 실행되지 않거나 릴레이 요청이 사라질 수 있다.

`manual_enable`을 사용하는 정상 보행 조건은 공통 `locomotion_enable`을 도입하거나 MANUAL/RL을 명시적으로 분리한다. RL을 외부에는 MANUAL로 표시하면서 내부 조건만 우회하는 구조는 피한다.

## 12. 함께 갱신할 문서와 구현 완료 조건

다음 기존 문서도 구현 범위에 맞춰 갱신한다. 조종 입력 및 제어 구조의 RL 설명은 후속 코드 작업에서 갱신했으며, v2 통신 규격 문서는 보존한다.

- `SW/STM32/STM32-Jetson SPI 32바이트 패킷 프로토콜.md`: v2 이력을 보존하고 v3 규격/샘플과 연결한다.
- `SW/Jetson/README.md`: 정책 추론, 128바이트 통신, 입력/출력 계약을 설명한다.
- `SW/Controller/드론 조종기 입력/README.md`: SB 표와 RL 입력 규칙을 갱신한다. 현재 “강화학습도 Throttle·Yaw·Roll·Pitch 스칼라를 사용”한다는 설명은 이번 다리 잔차 방식과 충돌하므로 교체한다.
- `SW/Controller/Controller_Architecture.md`: 같은 기존 RL 스칼라 입력 설명을 두 축 조종 명령과 자세/다리 잔차 구조로 갱신한다.
- `SW/STM32/STM32 코드 구조 정리본.md` 및 관련 제어 설명: RL 명령원, 공통 보행 허가, 기본 계획과 잔차의 연결을 반영한다.

구현 전에는 정책의 실제 관측 벡터, 축/다리 매핑, Tripod 기준 파라미터, 잔차·자세 한계, 세션 발급 방식을 확정한다. 학습 모델과 학습 코드가 현재 Jetson 폴더에 없으므로 이 항목들은 기존 모델에서 확인한 사실이 아니다.

구현 완료 확인에는 다음 항목을 포함한다.

- 양쪽에서 같은 바이트 벡터를 사용한 CRC·signed 정수·스케일·다리 순서 검증과 128바이트 DMA 교환 확인.
- 중복·역순·65535→0 순환·CRC 오류·잘못된 종류/예약 비트·이전 세션·오래된 관측·계획 불일치·정책 중단·부분 SPI 거래 검증.
- SB 1 서기 후 SB 0 RL, 미기립 SB 0, 첫 명령 대기, SE READY, SB 2 착지, SD Kill, Fault, CRSF 단절, Jetson 재시작과 재진입 검증.
- 잔차 0과 자세 목표 0에서 동일 조건의 기존 기본 보행이 재현되는지 확인. 각 다리 dx/dy/dz와 dh를 따로 적용해 착지점 변화와 들어 올림 높이 변화를 구분한다.
- 같은 계획을 반복 수신해도 잔차가 누적되지 않고, 검사 중 후보가 고정되며, 지지발과 진행 중 Swing이 새 패킷으로 점프하지 않는지 확인.
- 경로 검증에 사용한 계획과 실제 위상 시작 계획/ACK가 같은지 확인하고, Early/Late landing·공통 Z 복구·작업공간 제한 상황을 검증한다.
- 실제 5 ms 제어 시간과 추론→명령→자세/위상 반영 지연을 측정해 전송 주기·관측 최대 나이·Timeout 제안값을 확정한다.

최초 작업의 산출물은 이 계획 문서 하나였다. 후속 코드 작업의 범위는 다음 절과 같다.

## 13. 통신을 제외한 구현 상태

### 13.1 반영한 제어 동작

- `ROBOT_MODE_RL`을 기존 enum 끝에 추가했다. SB 0은 서기 완료·연결·입력 허가·새 0.2초 중립 확인 후 RL을 선택한다. SE READY·착지·Kill·Fault는 상위 우선순위를 유지한다.
- RL에서는 기존 Throttle/Yaw 필터와 부호를 사용해 전후·회전 명령만 만들고 Tripod 패턴을 고정한다. 사용자 Roll/Pitch는 무시하고 정책의 절대 자세 목표를 사용한다.
- `locomotion_enable`로 RL을 기존 보행·자세·접촉 처리에 연결했다. 초기 영점 정렬과 시험 단계의 RL 차단, 서보 릴레이 운용 모드 허가를 함께 반영했다.
- `RlController`가 내부 명령의 세션·관측·계획·새 순번·유한값·허용 범위를 검증한다. 중복 및 잘못된 명령으로 유효시간을 갱신하지 않는다.
- `WorkspaceLimiter`가 기본 계획을 먼저 공개하고 해당 계획의 잔차를 기다린다. 선택한 후보는 9개 경로점에서 주기당 최대 3점씩 검사하며, 실패한 기준 속도를 자동으로 바꾸지 않는다. 새로운 순번의 후보로 재시도한다.
- `FootTrajectory`는 검증한 끝점과 높이를 다음 Swing에서 한 번 고정한다. 지지발·진행 중 Swing에 새 잔차를 누적하지 않으며, `landing_target_z`에도 수정한 착지 Z를 사용한다.
- 정책 중단 시 현재 Swing의 착지를 마치고 반대 Tripod의 추가 이륙을 차단한다. 자세 명령을 제한 속도로 영점 복귀시키고 READY/ARM에서도 종료 시 발 위치를 보존한다. 이후 착지 요청은 복구 Swing을 거쳐 하강한다.
- 조종 입력이 중립으로 돌아오면 정책을 기다리던 이전 이동 계획도 취소한다. 이미 이륙한 발만 착지를 마치고, 다음 이동 입력에서 새 기본 계획을 만든다. 정책의 자세 전용 명령은 정지 중에도 받을 수 있다.
- Late Landing 한계에서는 위치를 유지한다. 모든 발의 접촉이 복구되고 SB를 RL 밖으로 옮긴 뒤에 정지 Latch 해제를 허가한다. RL 재진입은 새 중립 확인과 새 세션을 요구한다.

경로 검사는 샘플 기반 검사다. 실제 접촉·공통 Z 복구에 따른 변화에는 기존 매 주기 작업공간·자세 제한·IK 검사를 계속 적용한다. 샘플 통과가 접촉을 포함한 모든 미래 상태를 보증하는 것은 아니다.

### 13.2 현재 설정값

| 항목 | 구현값 |
|---|---|
| 정상 새 정책 명령 Timeout | 100 ms |
| 관측 최대 나이 | 60 ms, 다리 위상 시작 직전에도 확인 |
| 관측 이력 | 최근 32개 |
| 정책 Roll·Pitch 목표 | 각각 ±15도 |
| dx·dy·dz·dh | 각각 ±0.03 m |
| 최종 Swing 높이 | 기존 0.05~0.25 m 제한 |
| 자세 변화율 | 기존 자세 제어의 30도/s 제한 |

설정은 `Core/Inc/common/robot_config.h`의 `ROBOT_RL_*` 상수에 있다. 제한 전 원명령이 범위를 벗어나면 거부한다. 다리 높이는 허용된 잔차를 더한 뒤 기존 최소/최대 높이로 제한한다. 정책 학습과 실기 시험에서 같은 한계를 사용해야 한다.

### 13.3 통신 연결 전 내부 API

`Core/Inc/app/hexapod_app.h`에 다음 API를 추가했다. **두 API는 ISR이 아닌 메인 루프에서 직렬로 호출한다.** DMA 완료 ISR에서는 원시 수신 완료만 표시하고, 추후 파싱을 연결할 때 메인 루프에서 제출한다.

1. `HexapodApp_GetRlObservation(handle, &observation)`으로 활성 RL 세션의 완성된 관측을 얻는다. 이 호출이 실제 제공한 관측의 순번·캡처 시각·계획을 검증 이력에 남긴다. 반복 읽기는 관측 시각을 갱신하지 않는다.
2. 관측의 `session_id`, `sequence`, `plan.plan_id`, `plan.swing_mask`를 참조해 `RobotRlAction_t`를 만든다. 기본 착지점은 `plan.nominal[]`, 기본 높이는 `plan.nominal_height[]`다.
3. 자세 전용 출력은 `leg_plan_valid=false`, 계획 번호·마스크·여섯 잔차를 0으로 둔다. 다리 출력이 있으면 `leg_plan_valid=true`와 해당 계획을 지정한다. `posture_reference_rad.yaw`는 항상 0이다. 보행 Heading은 조종기 회전 명령 경로가 유지한다.
4. 새 추론마다 `sequence`를 증가시키고 `HexapodApp_SubmitRlAction(handle, &action)`을 호출한다. 수락 결과는 이후 5 ms 제어 경계에서 소비한다.
5. 자세의 `pose_sequence`와 실제 위상의 `leg_sequence`, `leg_plan_id`, `leg_mask`를 구분해 확인한다. 자세 목표 수락은 물리적으로 목표각에 도달했다는 뜻이 아니다.

현재 세션 번호는 한 번의 부팅 안에서만 재진입을 구분한다. 재부팅 이전 패킷을 구분하는 세션 교환, wire 순번/상태 매핑, 추론 실행기, 실제 Jetson 모델 연결은 패킷 구현 단계에서 완성해야 한다. 기존 SPI Raw Payload를 이 자료형으로 캐스팅하거나 memcpy해 제출하면 안 된다.

**현재 v2 SPI 명령은 이 API에 연결하지 않았다.** 따라서 SB 0 모드와 검증된 제어 경로는 준비됐지만, 정상 내부 정책 명령이 없으면 실제 RL 걸음을 시작하지 않는다. 기존 `jetson_spi.h/.c`, 32바이트 크기·CRC·DMA 교환·v2 프로토콜 문서는 변경하지 않았다.

### 13.4 검증 범위

신규 입력·모드·위상 정지·잔차 계획 시험을 추가하고 기존 보행·작업공간·제어기 시험과 함께 확인한다. `TestRunner`에는 `RL_INPUT`, `RL_STOP` 단계를 추가했다. STM32CubeIDE는 기존 `Core` 소스 경로에서 신규 C 파일을 포함한다. 외부에 별도로 고정한 소스 목록이 있으면 `rl_controller.c`, `rl_controller_test.c`, `rl_stop_test.c`를 포함해야 한다.

ARM GCC로 전체 펌웨어를 컴파일·링크했고, ARM 에뮬레이터에서 ModeTransition·RlController·RlStop·Gait·Workspace·Controller·Kinematics·Safety·UserCommand의 9개 제어 시험이 통과했다. 기존 모드 전환 시험의 오래된 속도 한계는 동일 입력의 새 제어기와 비교하도록 바꿨고, 기존 Late Landing 시험은 5 ms마다 최대 0.6 mm씩 움직이는 양자화 범위를 반영했다. 두 시험의 해당 제어 동작은 변경하지 않았다.

실제 앱 소스를 사용하는 임시 ARM 에뮬레이션 시험에서도 첫 정책 대기·이륙 직전 후보 만료·보행 중 Timeout·수동 Wave에서 RL 진입·Late Landing 접촉 복구·중립 입력의 대기 계획 취소 등 6개 통합 경로가 통과했다.

빌드 및 에뮬레이터 시험은 실제 보드의 전송 지연·5 ms 실행 시간·서보 동작 검증을 대신하지 않는다. 이 작업에서는 보드 플래싱과 물리 구동을 수행하지 않는다.
